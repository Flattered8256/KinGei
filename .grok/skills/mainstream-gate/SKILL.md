# 方案门槛

目的：不让"能跑通但非主流"的实现悄悄进入仓库。**先对齐，再动手。**

## 何时必须停下

满足任意一条：

- 用户想要的，已有成熟实现，但要求换一种做法。
- 需要自己实现 HTTP 语义（游标分页、`Range`、重试、限流、multipart）、UI 基础件（弹窗、开关、虚拟列表、Toast）、协议或状态机。
- 实现会让结构为单个特例变形：service 里塞 `if`、给某个页面开特例、在 repository 里拼业务判断。
- 同一件事仓库里已经有两套写法，用户要求写第三套。
- 需要新增依赖，或需要绕开框架约定（比如不用 Nuxt 的 `composables` 而自己做全局单例）。

## 输出格式（固定，一次说清）

```
主流做法：<库名 / 框架特性 / 同类项目（Mattermost、Rocket.Chat、Immich）怎么做的>
你的需求：<一句话复述，确认理解无误>
差距与代价：<多写多少代码、要自己维护什么、失去什么（可访问性、i18n、兼容性）>
选项：
  A 主流：……（推荐，理由）
  B 按你说的：……（代价是 ……）
  C 折中：……
```

写完就停，等回复。**不要**在消息末尾附上"我已经顺便写好了"。

## 怎么判断什么是"主流"

1. 官方文档和官方 examples 优先于博客、优先于记忆。
2. 先看依赖里有没有：`kingei-axum/Cargo.toml`、`kingei-nuxt/package.json`。已经有 `element-plus` 却手写组件，就是典型失败。
3. 搜同类开源项目怎么做的，看它们的目录结构和依赖。
4. 拿不准就写"我不确定，建议先查证"，不要编一个库名或版本。

## 已确认之后

在回复开头写一行决定，例如：

> 采用 A：用 `ElSwitch`，不为单个页面写自绘开关。

理由进提交信息或该行即可，不要写成大段注释。

## 例子（本仓库真实发生过）

用户要求"设置页加个开关"。

- 错误做法：新建 `KgSwitch.vue`，自己写 `role="switch"`、aria、过渡动画。
- 正确做法：先查 `package.json` → 有 `element-plus` → 用 `ElSwitch`；若设计稿差异大，再讨论是否做薄封装 `KgSwitch`（内部仍用 `ElSwitch`），并说明为什么不能直接用。

## 禁止

- 不要因为"已经写了一半"就跳过确认。
- 不要把选项写成伪选择：B 明显不可行就不要列出来凑数。
- 未确认前可以查资料、读源码、写 demo；**不能**改业务代码。
